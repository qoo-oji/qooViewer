# 05. ページ画像の表示とメモリ

## PageLoader(actor)

1冊につき1つ。責務は次のとおりで、**actor の隔離境界を壊さない**ことが最重要です。

- 書庫の reader と `CGPDFDocument` を actor の中に閉じ込める(スレッドセーフでないため)。
- デコード(`ImageDecoder`)は CPU 負荷が高いので actor の**外**の `Task` で行う。actor を
  ブロックすると他のページの要求が全部待たされる。
- 同じページへの同時要求は1つにまとめる(in-flight の辞書)。
- 同時デコード数を絞る: フル画像 2、サムネイルは CPU コア数。表示の要求は先読みより先に
  割り込む。
- 結果は3つの `PagePixelCache` へ入れる(ページ画像/進捗バー用サムネイル 240px/グリッド用
  サムネイル)。ページ画像の上限は環境設定(既定 300MB、1冊あたり)、件数上限 64。
- 現在ページの前後(環境設定「先読み」、既定 3)を先読みし、進行方向を優先する。速い
  ページ送りで不要になった先読みはキャンセルする。
- `releaseAllResources()` で全部を手放し、以後の要求を空振りにする(`isReleased`)。

## ImageDecoder ―― 解像度の上限

| 用途 | 長辺の上限 | 備考 |
|---|---|---|
| ページ表示 | 4096px | 表示に十分。それ以上は高解像度ソースへ |
| 進捗バー用サムネイル | 240px | ディスクキャッシュの対象(OFF の間は問い合わせも書き込みも作らない) |
| グリッド用サムネイル | セル高さ×画面倍率を 120px 刻みで量子化、240〜720px | ぼやけ対策と再デコードの抑制 |
| ホバーの拡大プレビュー | 枠(440〜800pt)×最大の画面倍率 | 以前は原寸(最大 47MB/枚)を使っていた |
| 高解像度ソース(拡大鏡・ピンチ拡大) | 8000px | 必要なときだけ取得し、不要になったら捨てる |
| 書き出し | 20000px | 実質無制限 |
| 実寸表示のウインドウ | 20000px(元の寸法が 4096px を超える画像だけ) | `PageLoader.actualSizeImage`。PDF は埋め込み画像の解像度まで、画像を持たないページは表示用のまま(2026-10-05 の監査 A3-2 ―― 以前は PDF の全ページを書き出しの上限で描き直し、文字だけの A4 で約 1.1 GB を作った) |

`kCGImageSourceShouldCache: false` で ImageIO のキャッシュを使いません(こちらで管理する)。

## PagePixelBuffer ―― なぜ CGImage を持たないのか

実測(→ [12](12-verification-and-debugging.md))で分かったこと:

- CGImage をそのまま表示すると、表示したページに CoreAnimation のテクスチャと CG のラスタコピーが
  付いて回り、**元の約3倍**のメモリになる。キャッシュ上限 300MB のつもりが 900MB 近くに膨らんでいた。
- malloc で確保した大きなブロックは、解放しても footprint が戻らないことがある。mmap/munmap なら戻る。
- ImageIO のサムネイルは purgeable。

そこで、キャッシュが持つのは **mmap 裏打ちの `NSData`(BGRA 8bit、またはグレー 8bit)**にし、
表示のたびに `CGDataProvider` で包んだ使い捨ての `CGImage` を作ります(`makeImage()`)。
CGImage が生きている限りバッファも生きるので、`ViewerViewModel.releaseResources` は
`currentImages` / `highResolutionSourceImages` / `loupeCombinedSourceImage` を明示的に空にします。
`LazyCellImageBudget`(下記)が要るのも同じ理由です。

`PagePixelCache` は **厳密な LRU**(NSCache は上限を守らない・追い出しの順が読めないため置き換えた)。
バイト上限と件数上限を持ち、メモリ逼迫の通知で刈り込みます。1枚が上限より大きい場合はその1枚だけ
残す仕様なので、リソースモニタの異常判定は3秒連続で超えたときだけ鳴らします。持続回数を進めるのは 1 秒ごとの拍だけで、
ディスクの走査の後・「今すぐ更新」の判定は回数を進めずに今の回数で見ます(`ResourceAnomalyDetector.evaluate(advancingStreaks:)`。
2026-10-04 の監査 SP-12 ―― 以前はそれらも数え、3 秒続く前に異常と出しえた)。

## 見開きの高解像度ソース

拡大鏡とピンチ拡大は 8000px 上限のソースを共有します。「拡大していない ⇄ 拡大している」を
またいだときだけ取得・破棄を切り替え(`updateHighResolutionSourceIfNeeded`)、ページが変わったら
取得の完了を待たずに古い結果を捨てます(どのページの像かを鍵の並び `highResolutionSourceKeys` で持つ。2026-10-04 の
監査 V-2 までは取得が終わるまで前のページの拡大像を出し、高解像度のデコードだけが失敗するとそのまま残った)。**見開きを1枚に結合した画像(最大 16000×8000×4 ≒ 512MB)は拡大鏡が ON の
間だけ**作ります(以前は無条件に作っていて、瞬間的に 1GB 近くになっていた)。

## 先読みと表示の順序

`ViewerViewModel.loadCurrentSpread` が世代番号で古い結果を捨て、`PageLoader.prefetch(around:
radius:displayedPageCount:direction:)` に「表示中の2ページの前後 radius 枚ずつ、進行方向優先」で
先読みさせます。素早い連続ページ送りでは `pageFlipQueue` に目的地を積み、通過ページを 10ms ずつ
実際に見せながら進みます(通過中は先読みしない。着地したページだけ本来のペア判定+先読み)。
通過ページのコマは、読み込みを待った後で「まだそのコマの番か」(`pageFlipGeneration`・`loadGeneration`・今のページ・取り消し)を
確かめてから出します(2026-10-04 の監査 V-1。以前は確かめずに出したので、積んだ最中のジャンプ・1 ページずらし・見開きの切り替えの後に
遅れて届いたコマが、移動先の見開きを通過ページの画像で上書きしていた)。
アニメーションのループは世代番号で中断できるようにしてあります(以前、目的地を追い越す形で
`currentIndex` が外から書き換わると無限ループになった)。

本全体の横長判定の下調べ(`warmUpWideImageCacheForEntireBook`)は、**最初の見開きとその周りの先読みを読み終えてから**始めます
(待つのは最大 10 秒。2026-09-25)。下調べも PageLoader の actor の上で書庫を読むので、同時に始めると表示と先読みがその後ろで待たされる
―― ネットワークボリューム上の本で、最初の見開きが数秒遅れた([plans/network-volume-study.md](plans/network-volume-study.md))。近傍の判定は
`primeWideImageCache` が最初の見開きと一緒に済ませます。

**ページの絵を待っている間は見せる**(2026-10-06 の応答性の点検 R1-1・R1-14)。`currentIndex` は押した瞬間に新しいページになるが、絵は
読み終えるまで前のページのまま残る。`ViewerViewModel` は `currentImages` がどのページのものかを `displayedImagesIndex` で控え
(`showImages(_:forIndex:)`。絵を出す経路はこれだけ)、今のページの絵が無いまま `pageImageWaitDelay`(0.4 秒。時限は
`DispatchQueue.main.asyncAfter` ―― `Task.sleep` はプールが塞がると発火しない)を過ぎたら `isWaitingForPageImage` を立て、ViewerView が
ページ領域に回転表示を出す(クリックは下へ通す)。最初の見開き(init の中では didSet が呼ばれないので明示して)も同じ。ふつうの本は先読みと
速いデコード(見開きで 0.1 秒前後)で出ない。読めなかったページは `unreadablePageIndex` で「このページを表示できません。」(以前は地の色
だけ)。**打ち切った先読みには表示の要求を合流させない**(`PageLoader.pixels`。打ち切られた読み込みも終わるまで `inFlightTasks` に
残り、合流すると nil を受け取って「表示できません」と出た。後始末は自分の Task のときだけ消す)。

## サムネイルの3段階

1. **進捗バー用(240px)**: プログレスバーのフィルムストリップとサイドパネルのページモード、
   編集ウインドウの行。`ThumbnailDiskCache`(既定 OFF、上限 200MB、`trimThreshold` の余裕付き)に
   載る。既定を OFF にしたのは、黙って数百 MB 使っていたことへの報告から。OFF のあいだは
   溜まっているものも削除する。OFF のあいだは読みの問い合わせも書き込みの Task も作らない。
   当たったファイルの更新日時(刈り込みの「最終アクセス」)は、1 時間より古いときだけ書き直す(`DiskCacheAccessStamp`、
   2026-09-25。以前は当たるたびに書いていて、プログレスバーを流すだけで 1 枚ごとにメタデータの書き込みが起きた。ファイル
   ブラウザの絵のディスクキャッシュも同じ)。
2. **グリッド用**: ページ一覧パネルのセル。セルの大きさに合わせた解像度。
3. **ホバー拡大プレビュー**: 4箇所(ページ一覧・サイドパネル・編集ウインドウ・書き出しウインドウ)
   共通の大きさと遅延。ディスクキャッシュには載せない。

本を開いた直後の下調べ(`warmUpWideImageCacheForEntireBook` → `PageLoader.scanPage`)は、寸法の
取得と**サムネイル生成を同時に**行います(飛ばすと近傍だけサムネイルが無い状態になる)。

## ソリッド 7z の読み方

7-Zip の既定はソリッド圧縮で、1ブロック=1本の LZMA ストリームです。フォーク
(→ [11](11-forked-dependencies.md))は前方へは無料で進めますが、後方は辞書(16〜64MB)の範囲を
超えるとブロック先頭からの伸長し直しになります。qooViewer 側の約束事:

1. 下調べは専用の reader で**書庫順**(現在位置→末尾、次に先頭→現在位置の手前)。前後交互は禁物
   (実測: 250MB・100 ページの cb7 で 275 秒 → 10 秒)。**取り出しは actor の外(FileIO の上)**(2026-10-06 の応答性の点検 R1-4):
   専用の reader は新しいので、最初の 1 件はブロックの先頭から再開位置までの伸長になり、actor の上で行うとその間ページ送りが全部
   待った(寸法を永続化していない初回と、永続化した寸法を読まないシークレットウインドウでは開くたび)。reader はスレッド安全でない
   ので `isScanReadInFlight` で 1 度に 1 本のスレッドしか使わない。サムネイルのディスクの鍵は取り出しの**前**に決める(待つ間に補正を
   切り替えられても、補正なしの絵を補正ありの鍵で残さない)。
2. 寸法は構造キャッシュへ永続化し、2回目以降は書庫に触らない。
3. 先読みは進行方向だけ。
4. ヘッダー情報は表示のために読んだバイト列から。
5. 「後方」の基準はデコーダの位置。

`residentDecompressionBufferBytes`(辞書+バッファ)はリソースモニタに「7z デコーダ」として出ます。
アクセス順を変えたら「ブロック先頭からのやり直し回数」を数えてください。

## コントラスト補正

本単位の設定(`BookLayoutSettings.contrastCorrectionEnabled`、既定 OFF)。`ContrastCorrector` が
デコード直後にチャンネルごとのオートレベル(黒点・白点を求めて引き伸ばす)を掛け、紙の黄ばみ
(青チャンネルの白点だけ低い)も同時に取ります。**カラーと判定したページには手を加えない**
(ユーザー要望)。ON/OFF はキャッシュを消して再デコードします。

## 拡大鏡(ルーペ)と GPU

`LoupeOverlayView` はマウス移動のたびに再描画が要るため、SwiftUI の `@State` を経由しない
生の `NSView`(`LoupeNSView`)で描きます(プログレスバーで「マウス移動のたびに `@State` を
更新するとメインスレッドが詰まる」を経験したため)。レンズの中の拡大は `GPUImageUpscaler`
(Core Image)で、画面のごく一部だけを対象にすれば Lanczos でも毎フレーム間に合います。
`CIContext` は生成が高いので1つを使い回します。

マウスの移動で描き直すのは、前と今のレンズの範囲(影の余白 12pt を足した和)だけです(2026-09-25 の監査。以前は
`needsDisplay = true` でビュー全体 ―― 見開き全面 ―― を毎回描き直し、`draw` はレンズに掛からない範囲でも何もせず返らなかった)。
`dismantleNSView` で閉包・画像・追跡範囲を外します(`NSViewRepresentable` の約束、→ [09](09-ui-and-windows.md))。

## 描画の実測から決めたこと

- SwiftUI の `Image.interpolation` は CALayer のフィルタに対応し、`.high` = `box`(面積平均)、
  `.medium` と `.low` はどちらも `linear`(同じ)。だから設定は「高品質/標準」の2択。
- ImageIO の縮小は `CG.high` 相当。
- 遅延デコードの直描きが最速。

## LazyCellImageBudget

SwiftUI の Lazy コンテナ(`LazyVStack` / `LazyVGrid` / `List`)は、画面外へ流れたセルの `@State` と
body の出力を破棄しません(300 セルで 170 個が生存)。`onDisappear` で nil を書いても、親を再描画
しても、`List` に替えても解放されないことを個別に確認しました。**唯一効いたのがコンテナに
`.id(epoch)` を付けて作り直すこと**で、Lazy コンテナならスクロール位置もずれません。
`LazyCellImageBudget` はセルが保持した画像のバイト数を数え、予算を超えたら `epoch` を進めます
(ページ一覧・サイドパネルのページモード・編集ウインドウの右ペイン・ホームのコレクションの一覧とスマートライブラリの
表紙のグリッドが使う。`List` だけは位置が先頭へ戻るので、自前で控えて復元する)。**画像を `@State` に持つ Lazy コンテナを
新しく作ったら、必ずこれを付ける** ―― スマートライブラリの表紙のグリッドは付け忘れたまま作られ、2026-09-22 の監査で
「数千冊を端まで流すと GB 単位が残る」と分かって足した(ファイルブラウザの表紙提供役の CGImage も mmap 領域を共有するので、
提供役のメモリの上限の外に積み上がる)。

一覧は `LazyCellImageBudget.ViewState`(`DynamicProperty`)で持つ: 数える帳簿は参照型で、`@State` なのは作り直しの番号(`epoch`)
だけ(2026-10-05 の効率の監査 B7)。帳簿そのものを値型の `@State` にすると、セルの絵が 1 枚届くたびに一覧全体の body が評価し直された。

## リソースモニタと異常検出

リソースモニタ(`ResourceMonitorView`)は、v1.29 で直した種類の過剰消費(設定を無視してメモリが膨らむ・
一時ファイルが残る)が再発したときに、ユーザーがひと目で気づけるようにするためのものです。2026-10-11 の点検
(利用者の要望)から、**メモリとディスクをどの機能がどれだけ使っているか**を機能ごとの折り畳めるまとまりで出します。

- **置き場所**: 本を開いている画面ではサイドパネルの「リソース」モード、ホームではインスペクタの上端の切り替え
  「情報 / リソース」(`WelcomeLibraryState.inspectorMode`、保存して次のウインドウが引き継ぐ。「メタデータの編集…」は「情報」へ
  戻す)。以前はサイドパネルにしか無く、ホームではサイドパネルが出ないので、ファイルブラウザ・ライブラリ・スマートライブラリを
  使っている最中に見られなかった。独立したウインドウではなくインスペクタの中で切り替えるのは利用者の指定。
- `ProcessResourceSampler`: `proc_pid_rusage`(自分宛てならサンドボックスで可)で CPU・
  メモリ(phys_footprint)・ディスク I/O を1秒ごとに計測。2分(1秒刻み)と1時間(10秒平均)の履歴。
  ネットワーク量と DB のメモリは公開 API では測れない。
- **メモリの内訳** `MemoryUsageRegistry`: メモリを意図して抱える持ち主が「自分の使用量を答える閉包」を届け出る
  (`MemoryUsageRegistration`。持っている間だけ載り、`end()`・解放で外れる)。モニタは 1 秒ごとに全員に尋ね、
  `MemoryUsageBreakdown` が機能(ビューア・補助ウインドウ・ホーム)ごとにまとめる。フットプリントから合計を引いた残りが
  「内訳の無いメモリ」(負になるとき = 帳簿より圧縮されているときは「—」)。テストでは届け出ない(`forCurrentProcess` が nil)。

  | 持ち主 | 機能 | 届け出の場所 |
  |---|---|---|
  | 本を読む `PageLoader`(3 つのキャッシュ・メモリ上の入れ子の書庫・7z のデコーダ。下調べ専用の reader の辞書も足す) | 作る側が `memoryUsageRole` で決める(ビューアの本・ブックマークとレイアウトの編集・書き出しのカバーの選択・書き出し・コレクションのカバーの作成) | `PageLoader.init` / `releaseAllResources` |
  | 拡大(ピンチ・拡大鏡)の高解像度画像 | ビューアの本の行へ足す(`role: nil`、同じ `ownerID`) | `ViewerViewModel` |
  | サイドパネル下段が自分で開く入れ子の書庫 | ビューア | `BookContentsBrowserState`(裏で reader を使っている間は前の値を答える) |
  | 実寸表示のウインドウの画像 | ビューア | `ActualSizePageView` |
  | ファイルブラウザとスマートライブラリのサムネイル・コレクションのカバー・タイルのメモリキャッシュ | ホーム | `AppStores.init` |
  | Lazy な一覧のセルが抱える絵(`LazyCellImageBudget` の帳簿) | 一覧ごと(`ViewState(byteBudget:memoryUsageRole:)`) | 最初に絵を数えたとき |

  一覧のセルの絵は**見積もり**(キャッシュの絵とバッファを共有していることがあり、作り直しの後に抱え直したぶんも数える)なので、
  「≈」を付けて出し、合計には足さない。本の名前はシークレットウインドウ・シークレットフォルダの本では出さない。
  **メモリを抱える新しいキャッシュ・画面を作ったら、ここへ届け出る**(届け出の無いものは「内訳の無いメモリ」に紛れる)。
- `ResourceMonitorSnapshot`: このウインドウの本の詳しい行(使用率のバー・先読みの帯 ―― 前方は「既読」として分けて
  見せる)の材料。`memoryOwnerID` で内訳の中のこの本の行を見分ける。**ほかのウインドウの本の行も同じ並び・同じ形**
  (3 つのキャッシュは 0 でもバー付き、入れ子・7z・拡大は使っているときだけ。違いは先読みの帯と過去のページが無いことだけ。
  利用者の指示: サイドパネルとインスペクタで同じ構成・並びに)。狭い幅では数値を名前の下の行へ回す(数値は切らない)。
  インスペクタの切り替えはサイドパネルのモード切替と同じ `PanelModeIconButton`(リソースは同じアイコン)。
- `StorageUsageScanner`: コンテナのディスク使用量を、機能ごとのまとまりで(ビューア: ページのサムネイル・ページ一覧 /
  ライブラリ: コレクションのカバー・指定したカバー画像・タイル / ファイルブラウザとスマートライブラリ: 絵のキャッシュ・
  スマートライブラリの一覧 / メタデータ: 規則・対象の本の記録 / 保存データ: DB・設定と履歴 / 一時ファイル: 入れ子の書庫・
  ネットワークボリュームの写し・前回の起動の残り)。シンボリックリンクは辿らない。15秒ごと。
  コンテナを 1 回だけ辿って内訳へ振り分ける(2026-09-25。以前は内訳ごとに辿り、合計のためにもう 1 度全体を辿った)。
  **容量はディスクの上で確保された量**(`DiskFootprint` = `totalFileAllocatedSize`)。ネットワークボリュームの写し
  (`StagedFileSource`)は本の大きさまで `ftruncate` するスパースファイルで、見かけの長さで数えていた頃は、開いた直後に
  本の大きさがそのまま「一時ファイル」に出ていた。ディスクキャッシュの刈り込み・環境設定「キャッシュ」の使用量も同じ数え方
  (上限は「ディスクをどれだけ使ってよいか」)。
  リソースモニタは App の `objectWillChange` の束(`AppStores.allObjectWillChangePublishers`)に入れない ―― 毎秒の発火が
  App の body とメニューを作り直していた。折り畳んだまとまりはアプリで 1 つの値(`ResourceMonitorFolding`、
  `qooViewer.resourceMonitor.collapsedGroups`。画面の状態なので保存データの書き出しには入らない)。
- `ResourceAnomalyDetector`: 誤報を出さない設計。メモリの上限超過は内訳の上限付きの全員を持ち主ごと・種類ごとに数えて
  3秒連続、先読みは「残留」ではなく「走っているタスク」で見る、ディスクキャッシュ(ページのサムネイル・ファイルブラウザ)は
  刈り込みの余裕を足した値を境目、刈り込みが間欠的なページ一覧のキャッシュ(起動ごとに 1 回)とタイル(数百枚ごと)は上限の
  2 倍、孤児の一時ファイルは走査2回(30秒)連続 ―― 入れ子の書庫は「本を読んでいる持ち主が内訳に 1 人もいない」、
  ネットワークボリュームの写しは「`StagedFileRegistry` が知っている数より多い」(閉じた後の 30 秒の猶予の間は登録簿が知っている)。
- 再描画コスト: 節ごとに `Equatable` な子ビューへ分け `.equatable()` で、毎秒描き直すのは
  グラフの節と「内訳の無いメモリ」の 1 行だけにしてある(以前はパネル全体の再描画で CPU 3〜5%)。

## 解放の連鎖(まとめ)

| きっかけ | 呼ぶもの |
|---|---|
| `ViewerView.onDisappear`、ウインドウの `willClose` | `ViewerViewModel.releaseResources()` → `PageLoader.releaseAllResources()`、表示中画像の破棄 |
| 編集ウインドウの右ペインの切替 | `BookLayoutEditorViewModel.releaseResources()` |
| 本を閉じる/切り替える | `BookContentsBrowserState.releaseResources()`(入れ子書庫の一時ファイル) |
| 本を閉じる | `ViewerViewModel.flushPendingSave()`(読書位置の保留分を確定) |
| Lazy コンテナの予算超過 | `LazyCellImageBudget.epoch` を進めてコンテナを作り直す |
