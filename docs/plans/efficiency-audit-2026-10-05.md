# 効率の監査 2 回目(2026-10-05)

[efficiency-audit-2026-09-25.md](efficiency-audit-2026-09-25.md)(1 回目)の後に入った機能(インスペクタ、シークレットフォルダ、ネットワーク
ボリュームの読み方、スマートライブラリの拡張など)を含めた全体を対象に、**機能と利用者の体感の速さを変えずに** CPU とメモリを減らせる所を探した。
範囲を 8 つ(ビューアのページ画像 / 本の読み込みと書庫 / ファイルブラウザとサムネイル / ホームのライブラリ・コレクション・インスペクタ /
スマートライブラリとメタデータ / アプリ全体の配線・永続化・メニュー / ウインドウごとの状態とサイドパネル / 書き出し・読み込み・ファイル操作・
自動リネーム)に分け、読むだけで候補を挙げ、1 回目の「見送ったもの」とコメントの却下理由に照らして残した。主な指摘は別にコードを辿り直して確かめた。

数字は特記の無い限りコードとコメントの実測値からの見積もり(実測ではない)。スマートライブラリの数字だけは合成データ 5 万件を
`swiftc -O` の単体計測で出した(5 万件の `localizedStandardCompare` の並べ替え 370 ms、3 欄のファセットの数え直し 233 ms など)。

凡例: 判定は **確認**(経路を全部辿った)/ **見込み**(UI フレームワークの振る舞い・大きさに依存)。段は「直した記録」の段。

## A. 効果が大きいもの

| ID | 判定 | 内容 | 段 |
|---|---|---|---|
| A1 | 確認 | **ソリッドな rar の本の初回の下調べが 2 乗**。下調べの専用 reader は 7z だけ(`PageLoader.scanReaderIfAvailable`)で、rar は `pageSize(at:)` → `dataPrefix` の既定実装 = エントリ全体の取り出しになる。unrar の 1 件ずつの取り出しは毎回書庫を先頭から辿り、ソリッドでは読み飛ばす項目も伸長する(2026-09-14 に `readEntriesInArchiveOrder` を作った理由と同じ)。その間 PageLoader の actor を握るので、ページ送りが後ろで待つ。→ rar の本は下調べを専用 reader で書庫順に 1 回だけ読み通す。 | 4 |
| A2 | 確認 | **スマートライブラリの `recompute` が操作のたびに全冊ぶんやり直す**。検索の 1 文字ごとにファセットの数え直し(5 万冊で約 230 ms)と全冊の並べ替え(約 370 ms)、棚の切り替えで全部の棚の冊数を数え直し(控えの鍵に選んでいる棚が入っている)、ホームへ戻るたびに同じ本の一覧でも控えを捨てる、選択が空でも 5 万件の配列と Set を作る(`pruneSelection`)、グリッドの body ごとに 5 万件の id の Set(`shownIDs`)。→ ファセット・並べた一覧・棚ごとの結果を控え、同じ本の一覧なら控えを残す。 | 2 |
| A3 | 確認 | **移動・改名の知らせの付け替え(`FileSystemChange.relocatedPath`)が組の数ぶん線形**。ファイルブラウザは選択の全パスに当てるので、多数を選んだままの一括リネーム・移動で「件数 × 件数」(2000 件でメイン 2〜4 秒、全ウインドウ)。保存データの付け替え(`BookRelocationPlan.make`)は `mayAffect` の早い除外無しで「記録のある全冊 × 組」(メインの外)。→ 段 1 で早い除外、段 3 で祖先の辞書引きに置き換える。 | 1・3 |
| A4 | 確認 | **本の書き出し(CBZ / EPUB / PDF)の中身がメインで走る**。3 つの `export` は `nonisolated async` だが `@concurrent` が無く、Approachable Concurrency の下では呼び出し側(`@MainActor` の `BookExportViewModel`)で走る。EPUB の画像の deflate、WebP などの PNG への変換、PDF の描画がメインを止める。→ `@concurrent`。出力のバイト列は同じ。 | 1 |
| A5 | 確認 | **保存データの読み込み・書き出しで、ファイルの識別子(inode)の照合が総当たり**。`resolvedURL(matching:)` / `bookmarkDataCandidates(matching:)` が 1 件ごとに各ストアの全行をなめる(メタデータの行数 × 他のストアの行数)。await の無いループでメインが止まる。→ 段ごとに inode の索引を 1 回作る。 | 3 |
| A6 | 見込み | **拡大(ピンチ・拡大鏡)と原寸大の高解像度画像を、ImageIO の CGImage のまま描いている**(実機で差が無く、戻した ―― 「実機の確かめ」)。`PagePixelBuffer` の型コメントの実測では、この形は CoreAnimation が写しとテクスチャを別に持ち続けて 3 倍になる(見開きのピンチで 1 GB 級)。→ `PagePixelBuffer` 経由にする。実機で footprint を比べてから。 | 4 |

## D. 振る舞いが少し変わるもの(利用者の判断待ち、今回は直さない)

## 棄却したもの(抜粋)

1 回目で見送った案(背面のタブのキャッシュを小さくする、`occlusionState` で止める、ページ送りの閉包の束ね、拡大鏡の結合画像をやめる、
グレーを 1 バイトで持つ、アクティブ化や書き込み中の読み直しの間引き、サムネイルの段どうしの縮小)は理由が今も当てはまるので挙げていない。
ほかに: ローカルの zip も `CentralDirectoryZipReader` で読む(壊れた書庫で一覧が変わる)、ページの並べ替えの鍵を前もって作る(並び・鍵を
揺らす危険に見合わない)、スマートライブラリの検索を `.literal` にする(書記素の境目で結果が変わる)、検索の入力を遅らせて間引く(見える遅れ)、
表紙の段を細かくする(画質と読み直しの兼ね合いで決め済み)、`ProcessResourceSampler` のタイマー(計測 ON のときだけ)、`DataUndoStack`
(上限あり)、copyfile の進み具合の報告(100 ms に間引き済み)。
