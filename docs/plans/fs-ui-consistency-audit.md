# ファイルシステムの実状態と画面の表示の食い違い ―― コード監査(2026-09-19)

きっかけは「ドラッグで移動したファイルの名前の編集が始まり、無いファイルが一覧に残った」不具合(同日修正、
[15](../15-file-browser.md) の「名前の編集を始める・続ける決まり」)。同じ種類の食い違いがほかに無いかを、
**ファイルシステムの状態を画面に写している場所を全部挙げ、それぞれ「誰が変更を知らせるか」「知らせを受けて何を読み直すか」
「パスで覚えている副次的な状態は何か」を追う**形で調べた。**同日、§6 のとおり修正した**(§1〜§5 は調査時点の記録のまま残す)。

凡例 ―― 根拠: **実測** = 一時的なテストを書いてテストホストで動かして確かめた(テストは消した) / **コード** = コードと既存の文書を読んで確かめた。

## 1. 構造上の原因(個別の指摘の大半はここから出ている)

ファイルブラウザができる前、ファイルシステムを変えるのは**必ずアプリの外**(Finder など)だった。だから
「アプリがアクティブになったとき・ボリュームの着脱で確かめ直す」で足りた(`CollectionStore` / `RecentFilesStore` / `FavoritesStore` の
コメントにそう書いてある)。いまは**アプリ自身がアクティブなまま**ファイルを動かす ―― ファイルブラウザの操作、取り消し・やり直し、
自動リネーム、圧縮・展開、書き出し。ところが「自分が変えた」ことを知るのは、操作をした `FileBrowserState` 1 つ(とそのツリー)だけで、
アプリのほかの部分へ知らせる口が無い(`FileBrowserOperations.didChangeFileSystem` は自分の `state` しか呼ばない。
`AutoRenameService.process` は誰にも知らせない)。ローカルのボリュームでは FSEvents が一部を補うが、見張っているのは
ファイルブラウザの右ペイン・ツリー・自動登録フォルダ・自動リネームだけ。

もう 1 つの原因は、**パスだけで覚えている状態**が多いこと(よく使う項目、戻る/進む、最後のフォルダ、カット、選択、名前の編集の依頼、
DB の `bookID`)。アプリ自身が名前を変えた・移したときは新旧のパスを知っている(`RenameReceipt` / `MoveReceipt`)のに、使っていない。

## 2. 指摘

### 高

**H1. アプリの中で移した本と、保存データ(棚・ブックマーク・レイアウト・メタデータ)の結び付きが切れる**(コード)
- DB の 5 モデルは `bookID`(パス)で引き、外れたときは `FileNodeIdentifier`(inode + ボリューム)で**本を開いたときにだけ**
  追従する(`reconcileBookIDIfMoved`。[06](../06-persistence.md)「移動・リネームへの追従」)。「ボリュームをまたぐ移動は諦める」と
  書いてあるのは、移すのが Finder だった頃の判断。
- いまはファイルブラウザ自身が別ボリュームへ移す(コピー + 削除で inode が変わる)。移した本は棚で「見つかりません」になり
  (`BookLocationResolver` は `.missing`)、**次の起動の掃除(`missingBookSweep`)の候補に挙がる**。ブックマーク・レイアウト・
  メタデータも新しい場所の本には付かない。アプリは移す前後のパスを知っているのに使っていない。
- 同じボリュームの中の移動・名前の変更は、棚の行はブックマークが追うので見つかるが、`bookID` と棚のキャプション(ファイル名)は
  その本を開くまで古いまま。ファイルブラウザの絵も `collectionStore.items(forBookID:)`(パス)で引くので、名前を変えた直後は
  棚の表紙ではなく自分で作った絵になる。

**H2. 棚・履歴の「実体があるか」は、アプリの中の操作では確かめ直されない**(コード)
- `CollectionStore.scheduleExistenceRefresh` / `RecentFilesStore.scheduleRefresh` / `FavoritesStore` の契機は起動・アクティブ化・
  ボリュームの着脱だけ。ファイルブラウザで本を移した・消した後にホームの棚へ切り替えても、アプリを離れて戻るまで表示は変わらない。
- ゴミ箱へ入れた本は、ブックマークがゴミ箱の中まで追うので `.found` のまま(`BookLocationResolver.resolve` のコメントに実測の記録)。
  棚では普通の本として表示され、開ける。ゴミ箱を空にするまで「見つかりません」にならない。仕様として残すかは判断が要る。

**H3. サイドパネルのフォルダブラウザは、外の変更もアプリの中の変更も一切読み直さない**(実測)
- `SidePanelBrowserState.reload()` が呼ばれるのは、移動・本の切り替わり・アクセス権の付与だけ。FSEvents もアクティブ化の読み直しも無い。
  表示中のフォルダに本を足しても、アプリを離れて戻っても一覧は変わらなかった。
- 一覧の読み込みの失敗を全部「アクセス権が無い」に倒している(`catch` で `needsFolderAccessGrant = true`)。**表示中のフォルダが
  消えると「このフォルダにはまだアクセスできません / アクセスを許可…」が出る**。ファイルブラウザの側は `FileBrowserLoadError.classify` で
  見分けて祖先へ退避する。

**H4. ビューアで開いている本を、別のウインドウ・タブのファイルブラウザで名前変更・移動・ゴミ箱にできる**(コード)
- 自動リネームは開いている本を避ける(`inUsePaths`)が、手の操作には同じ確認が無い。
- 起きること: ウインドウの題・サイドパネルの強調は古い名前のまま。「次の本 / 前の本」は一覧に今の本が見つからず黙って何もしない
  (`SiblingFinder.url(steppingBy:)` が nil)。フォルダの本はページをパスで読むので、名前を変えた後に読むページが出なくなる
  (zip は開いたハンドルで読み続けられる)。読書位置などは古い `bookID` で保存され、次に開いたときの追従頼みになる(別ボリュームなら H1)。

### 中

**M1. 表示中のフォルダの祖先が名前変更・移動されても気づかない**(実測)
- FSEvents は `WatchRoot` を付けていない(ファイル記述子を祖先の数だけ握るため。`FolderChangeWatcher` のコメント)。祖先の名前が変わると、
  右ペインは**もう無いフォルダの一覧を出したまま**になり(`revision` 変わらず、`currentFolder` は古いパスのまま、を確認)、
  パスバー・題も古い。どの操作も「見つかりません」で失敗する。アクティブ化で直る。
- 外の操作だけなら従来どおりの制限だが、いまは**アプリの中から起こせる**: 別のウインドウ・タブでの移動や名前の変更、
  取り消し・やり直し、フォルダの名前も変える設定の自動リネーム。

**M2. カットの記憶がウインドウごと**(実測)
- `cutPaths` は `FileBrowserState` ごと。ウインドウ A でカット → ウインドウ B でペーストすると、B のカットの記憶は空なので
  **移動ではなくコピーになる**(元も先も残る)。A の一覧はカットの淡色のまま残る。

**M3. 絞り込み中の新規フォルダと、残り続ける名前の編集の依頼**(実測)
- 絞り込み中に新規フォルダを作ると、できたフォルダは絞り込みで見えず、`renameRequest` が残る。**後で絞り込みを解いた時点で
  名前の編集が始まる**。reveal は「選んだのに見えない、を作らない」ために絞り込みを解くが、新規フォルダは解かない。
- 一般に `renameRequest` は「その id が一覧に現れるまで」残る(フォルダを移れば捨てる)。右クリックから頼んだ直後に項目が消え、
  後で同じパスに別の項目ができると、そこで編集が始まる。

**M4. パスだけで覚えている場所が、アプリの中の名前変更・移動に追従しない**(コード)
- よく使う項目(`FavoriteLocationStore`)、戻る/進むの履歴、最後に表示したフォルダ、コレクションの自動登録フォルダ
  (こちらは既知の制限として記載あり)。よく使う項目のフォルダそのもの・その祖先をアプリの中で動かすと、行は古い名前のまま残り、
  押すと祖先へ退避する。無くなったよく使う項目の行には印が無く、開くと空。

**M5. ネットワーク上のフォルダは、アプリの中の別の場所で起きた変更も届かない**(コード)
- 既知の制限は「外での変更はアクティブ化まで出ない」。同じ理由で、別のウインドウの操作・自動リネームの結果も届かない
  (ウインドウを切り替えてもアプリはアクティブなままなので、アクティブ化の読み直しも走らない)。

### 低

- **L1. 孫の変更で、フォルダの行の変更日・並び・フォルダの絵が古いままになる**(実測)。右ペインが読み直すのは「フォルダ自身か直下」
  だけ。サブフォルダの中にファイルが増えるとサブフォルダの変更日は変わるが、一覧の日付も変更日順の並びも変わらなかった。
  ツリーは 2026-09-17 に同じ件を直してある(`reloadExpandedRows` の `parentIDs`)。自分の操作の後は必ず読み直すので、外の変更
  (ダウンロード・自動リネーム)のときだけ。
- **L2. カットの淡色が古くなる**(コード)。ほかのアプリでコピーしてペーストボードが替わっても、カットした項目が外で消えても淡色のまま。
  判定(ペーストボードの集合と一致したときだけ移動)は正しいので、食い違うのは見た目だけ。
- **L3. 見張りを張り始めるまでの空白**(コード)。初めて張るストリームは `SinceNow`。一覧の列挙とストリームの生成は別々の非同期なので、
  その間(通常は数十ミリ秒、応答しない共有なら長い)の変更は取りこぼす。列挙の前にイベント ID を控えて `sinceWhen` に渡せば埋まる。
- **L4. イベントがあふれたときの扱い**(未確認)。右ペインは `init(onChangedPaths:)` でフラグを捨てている。`MustScanSubDirs` /
  `UserDropped` のパスが表示中のフォルダより上だった場合は読み直さない。実際にどのパスで届くかは測っていない。
- **L5. 絞り込み中のペースト・展開・圧縮の結果が見えない**(コード)。効果音は鳴るが一覧は変わらない。設計どおりだが、今回の報告と
  同じ「鳴ったのに見た目が違う」になる。
- **L6. 「同じフォルダのファイルを開く」の一覧は本を開いた時点のもの**(コード)。前後の本への移動は毎回読み直すので正しい。
- **L7. ファイルブラウザから出したメタデータ・書き出しのシートは、出した時点の項目を持つ**(コード)。開いている間に名前が変わると
  古いパスで保存する。
- **L8. 「名前を変更」の依頼・右クリックのメニューは、組んだ時点の項目を持つ**(コード)。操作は入り口で失敗して報告されるので害は無い。

## 3. 調べて問題が無かったところ

- 右ペインの読み直しの重なり(世代番号、読み込み中に届いた変更は読み終えてから 1 回、選ぶ依頼の持ち越しは 1 度だけ)。
- 表示中のフォルダが消えたときの退避(祖先へ、ボリュームごと外れたらコンピュータへ)。ボリュームの着脱・名前の変更。
- FSEvents のパスの突き合わせ: `/private`・`/System/Volumes/Data` の書き方、記号リンク、**大文字小文字の違うパスを「フォルダへ移動」で
  打った場合**(`resolvingSymlinksInPath` が実際の綴りへ直すことを実測)、NFC / NFD(Swift の `String` の比較は正準等価)。
- ツリー: 変わった項目の親の行の読み直し、閉じた行の三角の調べ直し、変更日順のときの親の行、Node の使い回し、共有の上の行のアクティブ化での読み直し。
- 絵: 鍵は更新日時とサイズ(メモリ)/ inode・更新日時・サイズ(ディスク)。作れなかった記憶も同じ鍵。セルの使い回しで別の項目の絵が残らない。
  アプリのアイコンの控えも更新日時つき。
- 操作の後始末: 成功・一部失敗・中止のどれでも一覧とツリーを読み直す。進捗の帯は操作に結び付く。ドロップの強調は読み直しで消える。
- 名前の編集中の一覧の凍結(今回の修正で、編集中の項目が消えたら取りやめるようになった)。一括リネームは押した時点で名前を決め直す。

## 4. 提案(構造から直す)

1. **アプリで 1 つの「ファイルシステムが変わった」の知らせ**(`AppStores` に置く値の流れ。仮に `FileSystemChangeCenter`)。
   中身は「変わったフォルダ」「移った・名前が変わった項目の新旧のパス」「消えた項目」「範囲が分からない」。
   - 出す側: `FileBrowserOperations`(実行・取り消し・やり直し。受領書から新旧のパスが取れる)、`AutoRenameService`、本の書き出し。
   - 受ける側と、直る指摘:
     - すべての `FileBrowserState`(自分のフォルダか祖先が含まれれば読み直す)→ M1 のアプリ起因、M5
     - `SidePanelBrowserState` → H3(あわせてアクティブ化の読み直しと、失敗の見分けを `FileBrowserLoadError.classify` に揃える)
     - `CollectionStore` / `RecentFilesStore` / `FavoritesStore` の実体確認 → H2
     - 5 つのストアの `bookID` の付け替え(新旧のパスで直接。別ボリュームでも効く)→ H1
     - `FavoriteLocationStore`・戻る/進む・最後のフォルダの書き換え → M4
     - 開いている本が含まれるビューア → H4(下の判断しだい)
2. **カットの記憶をアプリで 1 つに**し、ペーストボードの `changeCount` と組で持つ(替わったら淡色も下ろす)→ M2・L2。
3. **名前の編集の依頼に終わりを付ける**: 読み込みが済んだ一覧にその id が無ければ捨てる、絞り込みで隠れているなら絞り込みを解く(reveal と同じ)→ M3。
4. 右ペインの見張りを `init(onEvents:)` に替えて、孫の「作られた・消えた・名前が変わった」で読み直す(L1)、あふれは祖先のパスでも
   読み直す(L4)、列挙の前のイベント ID から張る(L3)。

## 5. 決めてほしいこと

- **H4**: 開いている本への操作をどう扱うか ―― (a) 自動リネームと同じく断る(開いている旨を伝える) / (b) 確認してから実行し、
  ビューアの側を追従させる / (c) 今のまま。(a) がいちばん小さく確実。
- **H2**: ゴミ箱の中の本を棚で「見つからない」扱いにするか(いまは普通の本として開ける)。
- **H1**: 別ボリュームへ移した本の保存データを新しいパスへ付け替えてよいか(取り消しで戻したら戻す)。

## 6. 対応(2026-09-19)

決定: H4 は (a) 断る、H2 はゴミ箱の中を「見つからない」に、H1 は別ボリュームでも付け替える。設計は
[15「アプリ自身の変更の知らせ」](../15-file-browser.md#アプリ自身の変更の知らせfilesystemchange2026-09-19)。

| 指摘 | 対応 |
|---|---|
| H1 | `BookRecordRelocator` / `BookRelocationPlan`。5 ストア + 読書位置を新旧のパスで付け替え(別ボリュームは inode とブックマークを取り直す)。使い捨てボリュームで実測 |
| H2 | 知らせを受けて棚・履歴・お気に入りの実体確認。ゴミ箱の中は `.missing`、開かない |
| H3 | サイドパネルが知らせ・アクティブ化・着脱で読み直す。消えたフォルダは祖先へ退避 |
| H4 | `FileBrowserOperations.refusesBecauseOpenInViewer`(名前の変更・移動・ゴミ箱・一括リネーム)。取り消し・やり直しは確かめない |
| M1 | アプリ起因は知らせで付いていく。アプリの外での祖先の変更は既知の制限のまま |
| M2・L2 | `FileCutClipboard`(アプリで 1 つ + `changeCount`) |
| M3・L5 | `settleRenameRequest`、置いた項目が見えなければ絞り込みを解く |
| M4 | よく使う項目・戻る/進む・最後のフォルダを付け替える。自動登録フォルダと自動リネームの対象・除外も付け替える(2026-09-22)。無い行の印は未対応 |
| M5 | 知らせで届く(アプリの外での変更は既知の制限のまま) |
| L1・L3・L4 | 右ペインの見張りを `onEvents` に替えて対応 |
| L6〜L8 | 未対応(15 の「既知の制限」へ) |

実機(Debug・使い捨てボリューム・合成名): ウインドウ B が `parent/child` を表示中に、ウインドウ A で `parent` の名前を変えると、B は退避せずに
新しいパスへ付いていき、その後に外から置いたファイルも出た。ビューアで開いているフォルダの本をゴミ箱へ入れようとすると断りのシートが出て、本は残った。
