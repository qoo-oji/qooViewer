# 画面の大きな切り替えの監査(2026-09-27)

ビューアとホームの行き来、新しいウインドウ・タブ、起動、フルスクリーン、ホームのモードの切り替えのように画面が大きく
変わるときに、意図しない描画の乱れ(小さいウインドウが一瞬出る、別の中身が挟まる、跳ぶ、何も映らないフレーム)や遅れが
出ていないかの総点検の記録(利用者の依頼)。

## 進め方

1. **洗い出し**(コードを読むだけ): 「ウインドウ・タブが出る経路」「既存のウインドウの中身の切り替え」「切り替えの途中で
   メインスレッドがする同期の仕事」の 3 つに分けて全経路を読んだ。
2. **実測**: 洗い出した切り替えを実物で起こし、フレームごとに記録した。
   - Debug ビルド・シークレットモード・使い捨てボリューム(`hdiutil`)に置いた合成の本(色の違う 8 ページの画像フォルダ 3 冊と cbz 1 冊)。
     Debug の保存データは本番の写しなので、ホームの本棚・スマートライブラリには実際の規模のデータが出る。
   - 使い捨ての観測ツール(リポジトリの外): `CGWindowListCopyWindowInfo` を 4ms おきに読み、このアプリのウインドウの出現・
     消滅・位置・大きさ・alpha の変化を記録。あわせて ScreenCaptureKit でこのアプリのウインドウ**だけ**を取り込み、
     フレームごとに 64×36 の濃淡の指紋だけを残す(画像は保存しない。文字は読めない解像度)。操作(メニュー・キー・`open -a`)の
     時刻を同じ時計で記録し、「操作の前のフレームとも最後のフレームとも違うフレーム」を途中の状態として拾う。
   - 数字の読み方: 操作からの時間には System Events でメニューを押す遅れ(約 250〜380ms)が含まれる。Debug ビルドなので
     アプリのコードは最適化されていない(遅さの絶対値は Release より大きい)。
   - 気づいた点: 1 フレームの長さは約 16ms(60Hz)。指紋の解像度では 1 行(40pt)未満の変化は拾えない。
3. 実測で確かめたもののうち、仕組みが単純なものをその日に直し、同じ条件で測り直した。

## 実測で問題が無かったもの

- ふつうの起動(ウインドウの出方。上の 1 のアニメーションの件を除く)
- ⌘N・⌥⌘N(元のウインドウに重なって出る。跳ばない)
- ウインドウ・タブを閉じる
- ビューア → ホーム(1 フレームで切り替わる)
- ツールバーの表示/非表示
- サイドパネルの表示/非表示(約 100ms の途中のフレームは、パネルが滑り出るアニメーション)
- フルスクリーンへの出入り(約 0.5 秒の途中は、システムのアニメーション)

## 測り直すには

観測ツールは使い捨て(リポジトリには入れていない)。作り方は上の「進め方」のとおりで、`CGWindowListCopyWindowInfo` の
4ms おきの読み取りと、ScreenCaptureKit(`SCContentFilter(display:including:)` でこのアプリだけ、まだ起動していないアプリを
待つときは `excludingApplications:` で今いるアプリをすべて除く)の 1 本の Swift ファイル。コールド起動を測るときはプロセス名
(Debug は "qooViewer Debug")でウインドウを探す。フルスクリーンの Space に入ると取り込みが止まることがある(出た後の
切り替えは取り直す)。フルスクリーンではタブバーが上端に残るので、ツールバーの帯と見間違えないこと。
